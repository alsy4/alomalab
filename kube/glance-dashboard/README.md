# Glance dashboard

Argo CD Application `glance` renders this directory with Kustomize from branch
**`kube`**, into namespace `glance-dashboard`. Merging a PR into `main` alone
does not deploy these changes. Publish the reviewed Glance commit to `kube`
through the normal review process, then inspect Argo CD reconciliation.

## Workload and configuration

Two replicas serve port 8080 behind Service `glance` and the Traefik Ingress
`glance.apps.alomalab.internal`. No PVC is required. Kustomize generates hashed
ConfigMaps from `config/*.yml` listed in `kustomization.yml` and `assets/user.css`;
changes to their references trigger a rollout. `assets-configmap.yml` and
`docker-compose.yml` are standalone artifacts, not part of the Kubernetes build.
The included pages are selected by `config/glance.yml`.

The Deployment pins the image digest observed on both healthy live Pods on
2026-09-24, avoiding an implicit upgrade from an unversioned image:
`sha256:9dfb09470b207dcb67ac715994bdb1929374ba3f9c0d7df7462c24adf10fd073`.
For upgrades, verify the upstream release and image digest, update the manifest,
and review the resulting rollout. This observed image runs on the current x86
VMs; check image platform support before introducing another architecture.

Startup, readiness and liveness use `/api/healthz` on the named `http` port.
The endpoint returned HTTP 200 in read-only live checks and is defined in the
[upstream server source](https://github.com/glanceapp/glance/blob/v0.8.6/internal/glance/glance.go).
Startup allows up to 150 seconds before liveness begins. The endpoint checks
HTTP server responsiveness, not each external widget dependency.

Each replica requests 25m CPU and 32Mi memory, capped at 250m and 128Mi.
The September 24 spot sample was 0–1m CPU and 10–13Mi memory; these settings
provide initial headroom, not a load-test guarantee. Review throttling, peak
memory and OOM events after rollout before tightening them.

## Secret prerequisite

The separately managed Secret `glance-proxmox` must contain key `authorization`
for `PROXMOX_AUTHORIZATION`. It is not generated by Kustomize. Provision it
before the first rollout. One option uses a local protected file containing the
Proxmox authorization value, avoiding a literal credential in shell history:

```bash
kubectl create namespace glance-dashboard --dry-run=client -o yaml | kubectl apply -f -
kubectl -n glance-dashboard create secret generic glance-proxmox \
  --from-file=authorization=/secure/path/proxmox-authorization \
  --dry-run=client -o yaml | kubectl apply -f -
```

Do not commit the file or generated Secret YAML. The Proxmox widget currently
disables upstream certificate verification; its token and access remain separate
from Caddy's browser-facing CA trust.

## Routing and verification

Pi-hole should resolve the hostname to Piloma `192.168.0.14`. Caddy terminates
HTTPS with its internal CA and preserves the hostname while forwarding HTTP
to Traefik. See the [Caddy ownership and migration runbook](../../ansible/README.md#glance-pi-hole-and-caddy-ownership).
DNS and Caddy are outside this Argo CD application.

```bash
kubectl kustomize kube/glance-dashboard
kubectl -n argocd get application glance
kubectl -n glance-dashboard get deploy,pods,svc,ingress
kubectl -n glance-dashboard rollout status deployment/glance-dashboard
kubectl -n glance-dashboard top pods
kubectl -n kube-system get svc traefik
```

For a direct application check, run `kubectl -n glance-dashboard port-forward
svc/glance 8080:8080`, then in another terminal:

```bash
curl --fail http://127.0.0.1:8080/api/healthz
dig @192.168.0.14 glance.apps.alomalab.internal +short
curl --fail --cacert /path/to/caddy-root.crt \
  https://glance.apps.alomalab.internal/api/healthz
```

For unavailable Pods, inspect `kubectl describe pod` and Deployment events for
missing Secrets, image pulls, probe failures, scheduling or OOM errors. For
working port-forward access but failed browser access, check DNS, CA trust,
Caddy ownership/upstream, and the Ingress Host match. Widget errors can occur
while health probes pass; check the upstream service and application logs.

Rollback by reverting the relevant commit on watched branch `kube`; Argo CD
self-heals direct workload edits. Confirm the previous digest and generated
ConfigMaps reconcile, both replicas become Ready, and HTTPS works again.
